用户给出一份**空骨架文档**（大纲有了、表格是空的），让你"根据这份文档干的事给我全量分析并填它"时，不要顺序地读骨架→逐节写内容，而是先把骨架视为**交付合同**，用一次大并行 Explore 反向驱动所有填充素材。

**Why：**
- 空骨架已经暗含了"你要关注的维度"（本次是 pre/prod 双阶段、高频功能、崩溃场景、恢复机制、阈值 5 个维度），这就是天然的子任务切分。顺序读→写会让主 context 被代码细节稀释，子节点之间缺一致标准。
- 骨架的所有节都依赖同一批底层事实（代码里 throw 在哪、catchError 多少、有没有全局 ErrorHandler、持久化 API 在哪），一次探索可喂饱所有节。分 N 次探索 = N 次冷启动 + 重复 grep。
- 用户说"全量"但不是真的跑测试—— 在本地文档类任务里，"全量"＝"现状盘点彻底"。识别这点能把路由从"开发→审查→交付"压缩成"调研→复盘"两步。

**How to apply：**

1. **读骨架先分节切维度**（5-8 个），每维度列"要回答的具体问题"。别发散，按骨架原样切。

2. **一次 Explore Agent prompt 覆盖全部维度**（medium 深度，不是 very thorough）。prompt 里强制：
   - 每节列出"关键文件:行号 → 功能点 → 状态（有/无/部分）"
   - 并行 Glob/Grep 关键字清单直接给出（throw / catchError / console.error / implements ErrorHandler / localStorage / IndexedDB）
   - 要数字统计（throw 几个、spec 几个、catchError 几个），不要泛泛形容
   - 报告上限（本次 800 行）—— 否则子 agent 会把代码贴进来稀释 context

3. **识别"伪模块"陷阱**：用户列的模块名可能是**业务视角**的（消息 / 任务 / 直播 / 会议 / 文档库 / 数据源 / 表单 / T度导向），而代码仓是**技术底座**（example-form-project 只做表单 + 数据源）。标注"不涉及本项目"比强行扯源码重要。判据：
   - grep 关键字 0 命中 → 伪模块
   - 仅在业务配置 YAML 里出现为字段名 → 伪模块（是"数据"，不是"功能"）
   - 只有主包的入口 route 有引用 → 伪模块（引擎的消费方，不是引擎本身）

4. **填文档时反用骨架结构**：不要重写骨架结构；用 Write 直接覆盖骨架文件（不是 Edit 逐节补），用 Explore 报告喂所有表格。表格行列 **按调研结果生成**，不按骨架的空行数。

5. **骨架已列的"不能 X 需签字"这种业务规则当硬约束留下**：本次骨架提到"不能恢复的需开发测试签字"，这是用户的**流程预设**，必须在成文里对齐（新增签字列/角色），不要自行删减。

6. **路由链路**：骨架驱动的调研填充 = **纯调研→复盘**，跳过设计/开发/审查/交付。判据：产出是文档，无代码改动，无需代码评审。

**反模式：**
- 逐节顺序 Read 骨架 → 开一个子 agent → 写一节 → 读下一节 → 又开一个子 agent：4 轮下来 context 爆了，每节风格还不一致
- 强行把"消息/直播/会议"在 example-form-project 里"找找看能不能对上号"：浪费轮次且会编造
- 骨架是空表格就照空表格列数填：骨架只表达关心的维度，不是行数合同

**成本参考（本次实测）：**
- 1 次 Explore（medium） + 1 次 Write + 1 次 handoff 更新 = ~3 次主轮次
- 产物：空骨架 → 完整文档（pre/prod 双阶段、15 项高频功能表、13 场景最坏/恢复、14 项监控阈值、4 周路线图）
- 比顺序填法省 3-5 轮，且各节引用同一批事实数字（throw=51/catchError=7/spec=62）完全一致
