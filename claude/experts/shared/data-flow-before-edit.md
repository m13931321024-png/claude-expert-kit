---
name: 跨层重构前先画完整数据流
date: 2026-04-20
type: pattern
---

修"多层 UI 协同显示"类 bug 时（典型如"左侧面板不更新 / 属性面板丢 setter / 画布不响应"），第一反应往往是找到表象所在层直接改。**实际上每个表象后面都挂着 2-4 层的协同**：注册表 → 消费端过滤规则 → 元数据合并 → 框架级覆盖 → 渲染器 ngOnChanges。**漏掉任何一层的 Localize 都会进入下一轮打补丁。**

**迭代预算警报**：如果同一类 bug 修了 2 轮还没收敛，**停**。回 Localize 重新画数据流——而不是继续打补丁。这是 Mythos "3 轮迭代预算"纪律的具体表现。

**怎么画数据流**（具体动作，不是空话）：

1. **找出所有消费点**：grep 该数据的生产者 + 所有消费者。例如"@FormWidget 注册的元数据"有几种消费路径：
   - palette 左侧面板（按 score / category / 去重规则）
   - metadataMerge（合并 design + runtime）
   - renderer 的 ngOnChanges
   - defaultProps 在新建节点时写入 node
   - YAML 导出时读 @FormWidget 元数据

2. **画出过滤/覆盖链**：每一层读数据时有什么过滤规则？
   - palette: `!w.hidden` + score 择优 + role 去重
   - metadataMerge: runtime 优先 + `inheritDesignProps` 截断 + 原型链回溯

3. **标红静默分支**：没有编译/lint 报错、只在运行时表现为"少一块"的路径。这些是下一轮 bug 的温床。

**Why**：跨层系统的 bug 本质是"我以为 A 层改了 B 层就响应，但中间还有 C 和 D"。LLM 倾向于就地改（看见啥改啥），把数据流画出来是对抗这个倾向的锚。SWE-Bench Pro 真实代码 17-23% vs Verified 70% 的差距，很大一部分就是多层协同的定位难度。

**How to apply**：
- 任何涉及 **注册表 / 装饰器 / 多 skin / 合并策略** 的修复任务，Localize 阶段必须输出一张 ≤ 10 行的数据流表（生产者 → 过滤层 → 消费者）
- 发现某个过滤层没有文档/注释 → 当前任务先读源码写明白，比直接改省两轮
- 每轮修复后，把"新发现的层"追加进数据流表，下次同类任务起点更高
- 超过 2 轮没收敛 → 强制整理成对比表（老行为 vs 新行为 vs 各层的响应），不写对比直接动手几乎必然超预算
